Mapping with EF Core

From model to relational schema

public sealed class Customer
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public ICollection<Order> Orders { get; } =
        new List<Order>();
}

public sealed class Order
{
    public int Id { get; set; }
    public int CustomerId { get; set; }
    public Customer Customer { get; set; } = null!;
}

EF Core connects the pieces

  • DbContext represents a unit of work and identity map.
  • DbSet<T> is an entry point for querying and tracking entity types.
  • Conventions, data annotations or Fluent API configure relationships and constraints.
  • Migrations capture schema changes; review and deploy them deliberately.
A navigation property is an object-model convenience; the foreign key is what enforces the relationship in the relational database.

Reliable transactions

ACID: what a transaction promises

Atomicity

All operations in the transaction succeed together—or none do.

Consistency

Committed work preserves database rules and constraints.

Isolation

Concurrent transactions behave according to the chosen isolation level.

Durability

Once committed, data survives failures as guaranteed by the database.

ACID is a property of database transactions—not a feature that an ORM can guarantee on its own. Provider, configuration and transaction scope matter.

EF Core in practice

Save once; group work intentionally

await using var tx =
    await db.Database.BeginTransactionAsync(ct);

try
{
    db.Orders.Add(order);
    await db.SaveChangesAsync(ct);

    db.OutboxMessages.Add(message);
    await db.SaveChangesAsync(ct);

    await tx.CommitAsync(ct);
}
catch
{
    await tx.RollbackAsync(ct);
    throw;
}

Key distinctions

  • A single SaveChanges is transactional by default when the provider supports transactions.
  • Two SaveChanges calls are not automatically one atomic operation; use an explicit transaction when both must commit together.
  • Keep transactions short; do not hold them open across slow external calls.
  • Use constraints and concurrency controls for correctness under concurrent requests.

The example rethrows failures so callers can handle them; production code should also apply the app's logging and cancellation conventions.

Application boundary

DTO: data shaped for a use

public sealed record OrderSummaryDto(
    int Id,
    string CustomerName,
    decimal Total);

var results = await db.Orders
    .Where(o => o.Status == OrderStatus.Paid)
    .Select(o => new OrderSummaryDto(
        o.Id,
        o.Customer.Name,
        o.Total))
    .ToListAsync(ct);

Why use a DTO?

  • Expose only the fields a client needs.
  • Decouple a public API contract from persistence details.
  • Shape list/detail views and avoid serializing entity graphs.
  • Validate incoming commands at the application boundary.
Project to a DTO in the query when practical: the database can return just the needed columns. A DTO is not automatically a security boundary—authorize and validate explicitly.

Persistence boundary

DAO: data access, not business policy

Data Access Object

A DAO encapsulates persistence operations for a data source: queries, inserts, updates and deletes.

  • Hides storage-specific details from its caller.
  • Can be implemented using EF Core or another provider.
  • Should not become a home for unrelated business rules.

EF Core already provides building blocks

  • DbContext tracks changes and coordinates persistence.
  • DbSet<T> supports common query and write operations.
  • Add a DAO/repository abstraction when it creates a meaningful boundary or behavior.
  • A wrapper that mirrors every EF method often adds indirection without value.
DAO vs. repository: terminology varies. A repository often expresses domain-oriented collection semantics; a DAO usually emphasizes data-source access. Neither pattern is mandatory just because an ORM is used.

Keep domain focused

Business rules should not depend on HTTP, SQL or EF Core implementation details.

Depend on abstractions where useful

Define ports at the inner boundary; let infrastructure implement them when replaceability or testing warrants it.

Choose boundaries pragmatically

Start simple. Introduce an abstraction to solve a real coupling, testing or domain-model need.

Takeaways

Use the right tool for the right boundary

ACID — reason about transaction scope and database guarantees.
ERD — make relationships and constraints explicit.
DTO — shape and protect boundary contracts.
DAO — isolate data access when that boundary has value.
EF Core — leverage its change tracking, queries and unit of work.
Architecture — keep business intent clear and dependencies deliberate.

Good design is less about adding patterns and more about making responsibilities explicit.
