A quick guide

Database concepts

Domain and data model

Entity

An entity is an object that represents something the application cares about and can identify over time. It has an identity and data; in a domain model, it may also enforce rules about how it can change.

For example, an Order entity has an ID, customer, and status. EF Core can map that .NET class to a database table and its instances to rows, but an entity is an application object—not just a row or a DTO.

Data access

DAO

A Data Access Object (DAO) is a way to organize database communication in dedicated code. It separates data retrieval and changes from application logic, centralizing operations such as creating, reading, updating, and deleting data.

DAO methods can be reused by different parts of an application for consistent data access. They may run SQL directly or use EF Core, which translates LINQ queries into SQL. In .NET, DbContext already provides data access: DbSet queries entities, changes are tracked, and SaveChanges sends updates to the database. A separate DAO is optional; avoid adding one if it only repeats EF Core's existing methods.

Data exchange

DTO

A Data Transfer Object (DTO) is a simple data shape for carrying selected information across a boundary, such as an API or between modules. Request DTOs describe input; response DTOs define the data the application chooses to expose.

Unlike an EF Core entity, a DTO is designed for the caller—not for persistence. It can omit internal fields, flatten relationships (for example, return a customer name instead of a customer object), and keep the API contract stable if the database model changes. DTOs are not tracked as entities by EF Core and normally carry data, not business rules. Validate input and authorize access separately.

.NET data tools

Entity Framework (EF)

Entity Framework Core (EF Core) is Microsoft's object-relational mapper (ORM) for .NET. It maps .NET entity classes to database structures, translates LINQ queries, tracks changes, and writes updates through a database provider.

A DbContext coordinates queries and changes; SaveChanges persists them. EF Core commonly connects a .NET application to a relational database, but it is not itself the database. Migrations help evolve the schema.

Reliable transactions

ACID

ACID describes four guarantees that help database transactions behave reliably:
  • AtomicityAll operations succeed together, or none of them do.
  • ConsistencyA transaction preserves the database's rules and constraints.
  • IsolationConcurrent work is separated according to the database's isolation level.
  • DurabilityCommitted changes persist, even after a failure.

EF Core's SaveChanges is transactional when supported by the provider. Use an explicit transaction to group multiple saves; ACID guarantees apply within that transaction.

Database types

Relational database

A relational database stores data in tables with defined columns. Primary and foreign keys connect rows; constraints protect rules such as required values and unique identifiers. SQL is commonly used to query and update the data.

EF Core is often used with relational databases such as SQL Server, PostgreSQL and MySQL. A transaction can update related rows together, while foreign keys help prevent references to missing records.

Database types

Document database

A document database stores records as documents, commonly JSON-like objects that can contain nested data. Documents can have different shapes, which can suit data that naturally belongs together or changes over time.

Examples include MongoDB and Azure Cosmos DB. Flexible structure is not the absence of design: the application still needs validation and clear ownership. Data modeling, querying and transaction guarantees differ from relational databases.

In summary

Different roles, one application

DTO carries data across a boundary. DAO provides a data-access boundary. EF Core maps .NET objects to a database. ACID describes transaction guarantees. Relational and document databases organize data differently.

In a modular monolith, keep each module’s rules and persistence ownership clear, use DTOs for deliberate communication, and choose a database model that fits the data.
